# CanTcpGateway

Cross-platform SocketCAN/CANable to TCP bridge for CAN debugging and integration tests.

The gateway forwards CAN frames from a configured `python-can` backend to every connected TCP client. Frames sent by any TCP client are transmitted through the CAN adapter.

## Requirements

- Python 3.10 or newer
- `python-can`
- Linux SocketCAN, CANable/SLCAN, or another supported `python-can` backend

Install the dependencies:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
```

## Start the gateway

Ubuntu with SocketCAN:

```bash
python3 can_tcp_gateway.py \
  --interface socketcan --can can0 --bitrate 250000 --port 29500
```

Windows with a PCAN adapter:

```powershell
py can_tcp_gateway.py --interface pcan --can PCAN_USBBUS1 --bitrate 250000 --port 29500
```

The default TCP bind address is `0.0.0.0:29500`. Authentication is intentionally not implemented because this bridge is intended for controlled test networks.

### Automatic gateway discovery

The client can discover a gateway automatically when no TCP host is supplied. The gateway listens for UDP discovery requests on port `29501` and returns the TCP address selected for the interface on which the client is reachable. This selection uses the operating system routing table and is portable across Linux, macOS, and Windows.

```bash
# Gateway (TCP 29500, UDP discovery 29501)
python3 can_tcp_gateway.py --interface socketcan --can can0

# Client using UDP discovery
python3 can_tcp_client.py --can vcan1 --create-vcan
```

The client retries discovery every three seconds until a gateway responds, and returns to discovery after a TCP connection is lost. Configure the ports and interval with `--discovery-port` and `--discovery-interval`. Supplying a positional host keeps the direct TCP connection mode:

```bash
python3 can_tcp_client.py 192.168.1.50 --port 29500
```

Discovery uses a signed-format-independent packet with a random token, so responses from stale or unrelated requests are ignored. UDP broadcast and the discovery port must be allowed by the local firewall.

## TCP frame format

Every CAN frame is represented by exactly 16 bytes. The layout is compatible with the Linux SocketCAN `struct can_frame` layout, with all multi-byte fields encoded in big-endian byte order:

| Bytes | Meaning | Format |
|---|---|---|
| 0–3 | `can_id` | unsigned 32-bit; `0x80000000` marks an extended ID |
| 4 | `can_dlc` | 0–8 |
| 5–7 | padding | three zero bytes |
| 8–15 | data | eight bytes; unused bytes are zero |

Example: extended CAN ID `0x18FEE8F0`, DLC 4, data `01 02 03 04`:

```text
98 FE E8 F0  04  00 00 00  01 02 03 04 00 00 00 00
```

TCP is a byte stream and may split or combine writes. Clients must read exactly 16 bytes for each frame. The protocol transports the CAN frame representation, not physical CAN bits such as SOF, CRC, or ACK; those are generated by the CAN adapter.

## Client and local CAN interface

The client exposes the remote CAN bus through a local CAN backend.

On Ubuntu, use a local `vcan` interface:

```bash
python3 can_tcp_client.py 192.168.1.50 \
  --port 29500 --interface socketcan --can vcan1 --create-vcan
```

Other local programs can then use `vcan1`. Frames received on `vcan1` are sent to the gateway, and frames received from the gateway are injected into `vcan1`.

If the interface already exists, omit `--create-vcan`:

```bash
sudo ip link add dev vcan1 type vcan
sudo ip link set vcan1 up
python3 can_tcp_client.py 192.168.1.50 --interface socketcan --can vcan1
```

On Windows, use the PCAN adapter through the `pcan` backend:

```powershell
py can_tcp_client.py 192.168.1.50 \
  --port 29500 --interface pcan --can PCAN_USBBUS1 --bitrate 250000
```

Windows has no built-in `vcan` equivalent. Creating a system-wide virtual CAN interface requires a vendor driver such as PCAN, Vector, or Kvaser. The TCP protocol itself is platform-independent. For a CANable in SLCAN mode, use `--interface slcan --can COM3` instead.

## Frame dump and filtering

Use `--dump` to print a readable view of traffic:

```bash
python3 can_tcp_client.py 192.168.1.50 --can vcan1 --dump
```

Example:

```text
14:22:31.084 RX  EXT 0x18FEE8F0 DLC=8 [FF FF 00 00 FF FF FF FF] J1939(prio=6, PGN=0xFEE8, src=0xF0, dst=global)
14:22:31.091 TX  EXT 0x0CE7F726 DLC=8 [01 02 03 04 05 06 07 08] J1939(prio=3, PGN=0xE700, src=0x26, dst=0xF7)
```

`RX` means a frame received from the gateway and written to the local CAN backend. `TX` means a frame read from the local CAN backend and sent to the gateway.

For high-rate traffic, limit output to selected IDs and cap the number of printed lines per second:

```bash
python3 can_tcp_client.py 192.168.1.50 --can vcan1 --dump \
  --dump-filter 0x18FEE8F0,0x0CF022F0 --dump-rate 50
```

The client automatically reconnects after a TCP disconnect. Change the retry delay with `--reconnect-delay 5`.

## GitHub Actions builds

The `Build CanTcpGateway` workflow builds both programs on Ubuntu 22.04, Ubuntu 24.04, and Windows after every push, pull request, or manual dispatch. Platform-specific backends are included:

- Ubuntu: `socketcan` only,
- Windows: separate `pcan` and `slcan` builds.

The Ubuntu artifacts are named `CanTcpGateway-ubuntu-22.04` and `CanTcpGateway-ubuntu-24.04`.

The workflow attempts to compress Linux binaries with UPX. UPX is skipped on Windows because PyInstaller executables use Control Flow Guard, which UPX cannot safely pack. UPX is a build-time optimization only and is not required on the target computer.

Artifacts contain:

- Separate `CanTcpGateway-*` artifacts containing the gateway binary.
- Separate `CanTcpClient-*` artifacts containing the client binary.
- `CanTcpBundle-*` artifacts containing both binaries and the README in a ZIP/tar.gz archive.

Download them from `Actions` → workflow run → `Artifacts`.

## Local quality checks

The project provides checks similar to the original Jenkins pipeline:

```bash
python -m pip install -r requirements-dev.txt
sh scripts/black.sh --check
sh scripts/check_code.sh
sh scripts/check_types.sh
sh scripts/run_tests.sh
```

To format the files automatically, run Black without `--check`:

```bash
sh scripts/black.sh
```

GitHub Actions runs these checks automatically in the `Quality checks` workflow before or alongside the build workflow.

For one command on Windows or Ubuntu, install the development dependencies and run:

```bash
python run_checks.py
```

To format the files first and then run all checks:

```bash
python run_checks.py --format
```

On Ubuntu, WSL, or Git Bash, the same operations are available through `make`:

```bash
make check     # Run all checks
make all       # Run all checks and build both applications
make format    # Format source files with Black
make lint      # Run Ruff
make syntax    # Check Python syntax
make test      # Run tests
make build     # Build standalone binaries with PyInstaller
make clean     # Remove local build and cache directories
```

`make build` uses `socketcan` on Unix-like systems and `pcan` on Windows. Override it explicitly with `make build BACKEND=socketcan`, `make build BACKEND=pcan`, or `make build BACKEND=slcan` when needed.

On native Windows, use `python run_checks.py` because `make` is not included with Windows by default.

## VS Code

The repository includes `.vscode/launch.json` with example debug profiles for SocketCAN, PCAN, and SLCAN. Open `Run and Debug`, select a profile, and adjust the host, CAN interface, or COM port for the local setup.

## Safety

Any connected TCP client can transmit arbitrary CAN frames. Use this bridge only on a controlled test network or test CAN bus, never on a production vehicle without additional access control.
